# 一句话机场演示与按需生成工具

状态：2026-10-01，演示场景和手机应用边界已由用户明确，具体实现与验收细节仍在提议阶段。初赛截止为 2026-10-04 23:59（北京时间）。本 packet 是当前任务接续入口；手机操作、运行时 Agent 和动态工具均未实现。

## 目标与授权

用户选择的最小场景是：“40 分钟内到机场，预算 50，尽量便宜。”用户强调没有指定机场与货币，这些需要自动补全。该场景承接混合步行、公交、地铁与打车的省钱目标。

用户新增硬边界：“不能我们自己接入地图、打车、地铁查询、日程、提醒...等服务，而是通过操作用户手机上既有的应用来完成。”这一要求约束所有数据读取和任务操作，包括动态生成的工具；不能绕过应用直接调用服务后端。

此前用户提出：“我们可以让 agent tools 动态地生成。安排 sub-agent(s) 去按需求动态地实现工具。”它指产品在任务运行时补全缺失能力，不等于由开发助手提前写好工具后声称运行时生成。

本轮用户询问方案判断，继续授权调查、方案讨论、task packet 维护和已确认知识回流。产品代码实现、宿主迁移和具体手机账户访问尚待明确。此前“你可以自由提交”适用于本轮文档提交；推送、发布与赛事提交仍不在本轮范围。

## 用户确定的边界

产品通过手机既有应用完成任务，复用地图的地点选择、路线呈现和导航交互。本地 OctoScript 约束表单仅用于开发调试。主 Agent 取得已授权的应用上下文、形成约束、组织查询与行动；新生成的工具也只能使用实际可用的手机操作能力与本地计算。动态生成不会创造应用未开放的数据或操作权限。

机场、币种和出发位置不能写死在提示词或工具中。演示可以事先在真实应用中设置明确标注的测试行程，但必须在运行时读取；准备上下文和授权的过程需在复现说明中交代。测试行程与应用在线返回的交通估价分别标明来源。

## 最小验收建议

下列是助手结合期限提出的范围，尚未成为已实现行为：限定一台手机、一个城市、一款地图和一个已有行程来源；地图若能提供公共交通及打车估价，就不另外增加应用。保持确定性时间／费用比较，先生成一个必要的应用操作工具，不建设通用手机编排平台。

1. 收到原句即记录时间，形成绝对到达期限 `received_at + 40 minutes`。用户已经登录相关应用并授权操作，但本次指令不补填机场或币种。
2. 从手机应用取得目的地、出发位置与币种依据，显示自动补全结果及来源。上下文足够明确的正常场景不中断询问；冲突或缺失只追问关键项。
3. 通过既有应用查询全公共交通、全打车以及至少一条合理的公共交通接打车候选。工具返回路段、交通方式、等待／换乘、耗时、估价与页面证据，确定性代码检查时限与预算。
4. 展示已核实候选中的最低估价及取舍，说明估价与读取时间。生成工具、查询和用户确认消耗的时间都计入 40 分钟；缺价不记为零，区间越过预算不能标成已满足约束，分段查询还需核对换乘衔接和未来乘车时段。
5. 用户确认后在既有地图进入对应导航，读回目的地、航站楼、交通方式与当前导航状态。混合方案需能表达对应路线或明确分段交接；不能最后打开默认驾车路线就算成功。不宣称演示已经证明实际到达或固定成交价。

首轮建议以规划、确认、进入匹配导航及读回为终点。自动叫车付款、提醒、长期偏好学习、持续路况重规划与多手机泛化留在后续范围；混合出行比较本身仍是本轮核心。一次有效候选查询不能证明全局最便宜，结果必须限定在已核实候选内。

### 自动补全的证据

| 缺失项 | 补全依据与边界 |
| --- | --- |
| 机场与航站楼 | 优先使用与当前任务相关的有效行程、日历或地图已有目的地，核对出发／到达机场、日期与航站楼。最近的机场或所在城市不能单独证明目的地；来源冲突时澄清。 |
| 出发位置 | 使用地图中当前定位或本次任务已明确的出发点，检查定位状态与新鲜度，不能把旧搜索位置当作当前位置。 |
| 预算币种 | 优先遵循已有明确偏好；否则结合本次出行应用的报价币种和地域上下文推断，并在结果中明示。界面语言不是币种；报价单位也不能在冲突时替代用户偏好。仅有有歧义的货币符号时需进一步取证。 |
| 到达期限 | 从接收指令的绝对时间起算 40 分钟；不能在生成或查询结束后重新开始计时。“到机场”不被替换为保证赶上航班。 |

### 动态生成工具的证据

建议选择当前地图应用的“路线查询与结果读取”工具：子 Agent 根据实际观察的页面和已有手机操作原语实现工具，先以一次新查询验证路段、时间、价格和页面证据，再交付主 Agent 查询不同候选。可复用的低层观测与操作通道需先存在；运行开始时该高层工具不存在。

保留需求、运行前工具清单、生成代码、验证结果、交付及实际调用记录。生成的工具不得自行增加地图等服务客户端；验证失败则保留未完成状态。只生成代码而没有实际调用，或输出未经页面证据支持的数据，均不算动态能力完成。

建议至少补一个机场来源缺失／冲突的失败场景，只追问机场而不继续执行；另在既有应用中更换行程后重跑，证明机场取自当前上下文而非硬编码。动态工具失败与预算不可行也应有明确状态，具体自动检查在实现方案确定后选择。
