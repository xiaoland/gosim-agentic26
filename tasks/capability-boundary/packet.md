# 出行能力层与按需生成工具

状态：2026-10-01，正在澄清方案与调查前提。已有本地开发闭环；跨应用集成和运行时工具生成均未实现。本 packet 是当前任务的接续入口。

## 目标与授权

目标是在既有地图或系统 Agent 中完成混合出行省钱任务，让系统获取已有背景、减少用户表达，并探索缺失工具能否在任务运行期间由子 Agent 实现。需要明确产品职责、真实接入途径和最小验证任务。

用户明确要求：“我们只是在一个既有的地图应用，或者在一个系统的层面去把各种 APP 组合起来”，重点仍是在限定时间内组合步行、公交、地铁和打车，以最低费用抵达目的地。随后提出：“我们可以让 agent tools 动态地生成。安排 sub-agent(s) 去按需求动态地实现工具。”这是拟议的产品运行机制，尚未确定实现方式，也不等于已经实现或授权启动产品开发子任务。

本次用户指出：“你似乎没有创建并维护一个 task packet”。当前授权包含维护本 packet、接通知识导航，以及把已确认的产品边界回流现有说明。调查与隔离实验可自主推进；具体能力实现与宿主迁移尚未获授权。此前“你可以自由提交”适用于本次文档提交，不包含推送、发布或赛事提交。

## 已确认方向与讨论中的方案

产品依托既有地图或系统完成任务，复用地图的地点选择、路线呈现和导航交互。Agent 从已授权的应用与系统上下文取得约束并组合能力，尽量减少用户表达。本地约束表单只用于开发调试，不能作为能力层成果。

用户新提出的机制是：主 Agent 发现任务所需能力缺失，委派子 Agent 根据需求实现工具，然后继续完成同一个任务。工具实现代码也随任务产生，不能仅以选择或组合预先准备好的工具来证明这一机制。

助手提出、尚待验证的具体流程是：检查实际可用接口与环境 → 实现具有明确输入输出的工具 → 在隔离环境验证行为 → 交给主 Agent 调用 → 读回任务结果。助手建议先保持出行优化算法稳定，让周围的应用接入、数据转换和小段任务计算按需生成；该分工不是用户已批准的架构决定。

动态生成解决能力如何产生，accessibility、视觉或 API 解决如何访问应用，两者可以结合。生成代码仍需依赖实际存在且已获授权的访问途径。示例中的日历工具、地图回传接口均为待调查对象，不能当作宿主现成功能。

## 待验证前提与下一步

| 不确定性 | 需要取得的证据 | 如何影响下一步 |
| --- | --- | --- |
| 目标宿主、地图、日历及城市尚未确定，现有接口能提供什么？ | 固定版本的接口或源码，以及授权条件下的一次真实调用；分别核对上下文读取、路线查询、呈现和执行。 | 选取实际可访问的一项缺失能力；没有访问途径时调整候选宿主或数据源，不能靠生成代码补出不存在的权限。 |
| 运行时能否让子 Agent 实现并交付一个新工具？ | 工具在任务开始时不存在；保留需求、生成代码、验证结果、交付方式及主 Agent 实际调用记录。 | 能成立才继续验证动态能力；预先写好工具或由开发助手离线补代码，只证明开发流程。 |
| 如何判断生成工具成功，失败时如何继续？ | 工具输入输出、访问权限与副作用边界可检查；有成功结果读回和一次生成或验证失败的可观察结果。 | 验证通过后才交付使用；失败应保留任务未完成状态，不能伪造执行成功。具体执行环境与验证方式待定。 |

下一步先调查一组可运行的宿主与应用接口，并据此提出一个有界实验。候选例子是“去下午那个会，尽量省钱”：主 Agent 缺少读取会议时间和地点的工具，子 Agent 根据真实接口实现并验证，主 Agent 随即使用返回的有来源数据继续出行任务。该例子只是实验候选；尚未选定日历、地图或模型服务，也未授权相应账户访问。

最小实验的验收提议是：从缺少工具开始，观察真实生成、验证、交付、调用和结果读回，证明主 Agent 在同一个任务内继续执行。若使用模拟调用方或交通数据，只能证明相应内部流程，不能据此宣称真实跨应用导航已完成。完整出行验收仍需有来源的路线与票价、截止时间内最低费用求解、用户确认、执行读回和条件变化后的重规划。
